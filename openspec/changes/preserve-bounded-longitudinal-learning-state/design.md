## Context\n\nUnsigned browser learners and the gateway's file-local adapter keep at most 500 learning events. Both currently use a plain newest-first slice. Once a learner produces more than 500 events, older activation, diagnosis, lesson-completion, training-resume, transfer, and practicum-completion evidence disappears even though current selectors still depend on those events. PostgreSQL keeps complete signed-in event history, but browser bootstrap immediately slices it and therefore loses the same milestones in the rendered product.\n\nThe event payload contract is already privacy-bounded: it excludes source code and free-form learner answers. The change must keep that contract, preserve exact evidence IDs, stay deterministic across browser/gateway/import, and avoid an unbounded local store.\n\n## Goals / Non-Goals\n\n**Goals:**\n\n- Keep all local event collections at or below 500 events.\n- Guarantee a recent-activity budget while reserving bounded capacity for the milestones used by current product flows.\n- Preserve exact validated events instead of synthesizing mastery or completion.\n- Apply the projection during parse, append, merge/import, file-store load, and file-store append.\n- Re-project complete PostgreSQL bootstrap history into the same browser view.\n- Prove parity with deterministic tests and longitudinal selectors.\n\n**Non-Goals:**\n\n- Do not replace PostgreSQL as the complete signed-in source of truth.\n- Do not claim unlimited offline history or preserve every intermediate event forever.\n- Do not add analytics tracking, code snapshots, free-form responses, or a new database table.\n- Do not redesign mastery, delayed-review, curriculum, or backup UI.\n- Do not mutate existing production PostgreSQL rows.\n\n## Decisions\n\n### 1. Use a bounded retention projection over exact events\n\nBoth local implementations will expose a pure `retainLearningEvents` function. It validates/deduplicates upstream, sorts by `createdAt` then `id`, projects a bounded set of longitudinal milestones, and fills every remaining slot with the newest non-selected events.\n\nThis is preferred over raising the limit because storage and privacy remain bounded. It is preferred over synthetic events because current UI, evidence links, exports, and teacher review can continue to reference the original event ID and payload.\n\n### 2. Reserve at most 200 milestone slots and at least 300 recent slots\n\nThe total hard limit remains 500. The projection selects at most 200 milestone events, then fills to 500 from newest remaining activity. If fewer than 200 milestones exist, recent activity uses the unused space.\n\nMilestone keys are deliberately semantic and compact:\n\n- earliest entrance lifecycle facts: first mission seen, reason acknowledgement, first run;\n- latest Mentor revision verification;\n- latest diagnostic result per diagnostic step;\n- latest lesson completion and transfer pass per lesson;\n- for lessons without completion, latest training start and latest completed event per training stage;\n- latest training-session completion per lesson;\n- latest mastery-check pass per problem;\n- latest practicum completion per project.\n\nCompleted lessons do not retain every intermediate training frame in the milestone reserve; those events remain only while recent. This preserves prerequisites and outcomes while bounding growth.\n\nIf more than 200 keyed milestones exist, the three earliest activation facts remain mandatory and the newest remaining milestones win. This explicit overflow behavior is preferable to silently exceeding the storage limit. PostgreSQL remains the recovery authority for signed-in users.\n\n### 3. Preserve format compatibility\n\n`LearnerMemory` remains version 1 and backups remain version 5 because the serialized shape does not change. Existing browser memory and backup imports are migrated by applying the new projection to all valid events available at parse/merge time. Evidence already absent from an old bounded backup cannot be recovered and must not be invented.\n\nThis is preferred over a schema-version bump because no new field or interpretation is required; only deterministic retention semantics change.\n\n### 4. Keep browser and gateway implementations explicit but contract-identical\n\nThe browser and gateway have independent TypeScript build roots. Each will contain a small pure implementation using the same named constants and key rules. Contract tests on both sides will use equivalent scenarios: more than 500 events, old activation facts, completed prerequisite, active training stage, transfer, project completion, duplicate ordering, and recent activity.\n\nA shared cross-package build dependency is deferred because it would add packaging complexity disproportionate to this pure policy. Strict tests and identical policy constants are the drift guardrail.\n\n### 5. PostgreSQL remains unbounded and authoritative\n\nPostgreSQL event rows are not compacted. On signed-in bootstrap, the frontend parser receives full events, projects them into the bounded browser view, and preserves recoverable milestones. File-local mode documents bounded durability and applies the retention projection before persistence.\n\n## Risks / Trade-offs\n\n- **[Milestone overflow beyond 200 keys]** → Keep activation mandatory, keep newest milestones, retain a minimum 300-event recent window, and rely on PostgreSQL for complete signed-in recovery. Record overflow behavior in tests and documentation.\n- **[Browser/gateway policy drift]** → Use the same constants, key table, deterministic ordering, and mirrored contract fixtures/tests; fail full verification on parity regression.\n- **[A selector relied on an unlisted old event]** → Add end-to-end selector tests for first-minute metrics, starter prerequisites, training resume, transfer scheduling, and practicum availability before switching retention.\n- **[Old backups already lost milestones]** → Never synthesize missing evidence; import only re-projects valid available history.\n- **[More CPU during append]** → The algorithm operates on at most roughly 501 browser events and 5,001 file-store receipts, with O(n log n) sorting. Measure a 5,000-event projection and require a practical local threshold.\n- **[Event ordering ambiguity]** → Sort by parsed timestamp and then stable event ID; reject invalid timestamps through existing validation before projection.\n\n## Migration Plan\n\n1. Add failing browser and gateway retention contracts plus longitudinal selector regressions.\n2. Implement pure retention functions without changing caller interfaces.\n3. Apply browser projection in parse and append; merge/import inherits it through those functions.\n4. Apply gateway projection in file-state load and event append; leave PostgreSQL unchanged.\n5. Bootstrap a signed-in learner from a synthetic full history and verify browser recovery.\n6. Run full tests, typecheck, lint, build, OpenSpec validation, and a 5,000-event performance probe.\n7. Roll back by restoring newest-500 slicing; no data migration or database rollback is required because serialization shape is unchanged.\n\n## Open Questions\n\n- Real production data is required to tune the 200/300 split. The initial split is a tested safety default, not a claim that it is optimal.\n- A future server-side aggregate analytics store may preserve cohort metrics independently of learner-facing event retention; it is outside this change.\n\n
