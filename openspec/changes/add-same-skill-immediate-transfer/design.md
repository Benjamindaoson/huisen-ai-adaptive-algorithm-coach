# Design\n\n## Decision\n\nThe first lesson receives a small function-writing challenge whose only algorithmic operation is sequential traversal. The page sends the complete source to the configured private runner twice, appending a different invocation for each case. The page never evaluates Python locally.\n\nThis is an immediate near-transfer checkpoint, not a real-problem mastery receipt. A pass records `training-stage-completed` for `transfer`; it must not create `lesson-transfer-passed`, because the latter remains reserved for an unassisted accepted submission bound to an immutable problem attempt.\n\n## Challenge boundary\n\nThe learner defines a function that prints each luggage weight in order. The task changes the surface and asks for a complete loop, while avoiding sorting, interval merging, hashing, or input parsing. Two executions use different array lengths and values.\n\n## Failure behavior\n\n- Compile/runtime/wrong-output results remain in the training cabin with concise evidence.\n- Runner unavailability is named as a service limitation and never advances the stage.\n- Only all-case success records the immediate transfer stage.\n\n## Mastery language\n\nThe replay may say that immediate transfer passed. It must also say that long-term retention remains unverified and must never equate this event with `lesson-transfer-passed`.\n\n
