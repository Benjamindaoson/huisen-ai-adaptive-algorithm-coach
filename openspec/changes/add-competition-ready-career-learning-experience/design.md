## Context

现有 React App 已有 Today、学习、练习、考试、能力报告和常驻 Mentor，学习事件可同步到权威后端。缺口不在算法题数量，而在用户无法直观看见个性化决策依据、教育数据边界，也没有一条脱离单题的真实工程任务链。比赛受众包含非专业评委，因此这些能力必须用普通语言、可点击页面和真实状态变化表达。

## Goals / Non-Goals

**Goals:**

- 三项能力均进入一级导航，移动端也能访问。
- 推荐由确定性、可测试的证据解释器生成；模型不得凭空编造推荐理由或修改掌握度。
- 项目实训复用语义事件、服务端 outbox 和 Mentor 上下文，刷新后能恢复。
- 数据与评价边界不仅写免责声明，还提供存储状态、采集范围、导出和删除的实际入口。

**Non-Goals:**

- 本阶段不建立 Git 托管、云 IDE、教师 SaaS 或招聘平台。
- 不把静态演示项目冒充真实外部仓库，也不让 Mentor 自动写入代码。
- 不宣称 AI 诊断已经通过真实教师质量门禁。

## Decisions

### 1. 用三个深模块而不是一个大型比赛展示页

`education-trust` 负责数据政策视图，`adaptive-plan` 负责推荐证据投影，`project-practicum` 负责项目状态机。页面只消费它们的类型化输出。这样产品文案、计算规则与 UI 可分别测试；相比把条件散落在 React 页面中，更容易证明“因材施教”不是装饰性文案。

### 2. 个性化理由由可解释规则生成

计划解释器读取目标、最近语义事件、技能信号、提示依赖和延迟复测，输出带 `evidenceRef`、置信度和替代行动的推荐。模型可帮助解释但不能拥有计划事实。无证据时必须显示基线计划，不能伪称个性化。

### 3. 项目实训采用阶段状态机和模拟仓库快照

首个实训使用一个受控、可执行的多文件 TypeScript 仓库快照，阶段为理解、定位、计划、实现、验证、复盘。学习者通过界面选择诊断、编辑补丁并运行测试；只有验证通过后才能完成。选择模拟仓库而不是接 GitHub OAuth，能在比赛环境稳定演示真实工程思维，同时明确标注数据为公开许可/模拟教学数据。

### 4. 数据控制入口复用已有导出/删除能力

信任中心读取当前平台能力和身份状态，调用现有账户导出/删除接口或打开对应账户操作；离线状态明确解释本地缓存。政策清单采用代码内版本化常量并显示生效版本，避免后端未实现时伪装成功。

## Risks / Trade-offs

- [单个模拟仓库不足以证明广泛工程能力] → 明确标注“首个实训”，设计可扩展清单结构，验收只要求完整闭环。
- [规则推荐看起来不像 AI] → UI 同时展示证据、数字孪生信号和 Mentor 可采取的下一步；技术感来自可验证适配，不来自生成文案。
- [数据删除可能是不可逆操作] → 页面只展示范围并要求进入账户安全流程确认，不提供无确认的一键删除。
- [项目编辑器与题目编辑器重复] → 首版复用轻量文本编辑和现有运行反馈模式，不引入新的编辑器依赖。

## Migration Plan

1. 先上线只读信任中心与推荐证据，不改变已有学习数据。
2. 加入项目实训本地进度和语义事件，通过现有 outbox 同步；旧备份缺字段时初始化为空。
3. 更新导航、备份 schema 和能力报告；如回滚，旧客户端忽略未知事件，已有题库/考试不受影响。
