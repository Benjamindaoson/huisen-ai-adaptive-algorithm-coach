## Context\n\nThe outbox is the durable bridge between browser learning state and authoritative platform APIs. Its current 1,000-operation slice is an optimization without backpressure semantics. It violates the outbox's most important invariant: an operation may leave the queue only after successful authoritative acceptance or an explicitly handled state conflict.\n\nLarge snapshots also assemble all writes before flushing. Merely throwing at a hard limit would deadlock synchronization because the client would repeatedly fail before it had a chance to drain the existing batch.\n\n## Goals / Non-Goals\n\n**Goals:**\n\n- Never evict an unsent operation because a newer operation arrives.\n- Bound the active enqueue batch at 1,000 operations without bounding readable legacy data.\n- Drain and continue the same snapshot automatically when the active batch is full.\n- Preserve duplicate, mutable coalescing, idempotency conflict, ordering, retry, and acknowledgement behavior.\n\n**Non-Goals:**\n\n- Moving the outbox to IndexedDB.\n- Parallel network writes.\n- Changing platform endpoints or server idempotency.\n- Claiming protection from browser storage deletion or physical device loss.\n\n## Decisions\n\n### Capacity is explicit and lossless\n\n`read()` returns every valid persisted operation. A new immutable operation or new mutable stream may be added only below the 1,000-operation active capacity. At capacity, enqueue throws a typed capacity signal before storage is mutated. Exact immutable duplicates and replacements of an existing mutable stream remain valid because they do not increase queue length.\n\n### Synchronization treats capacity as a batching boundary\n\nSnapshot assembly uses an enqueue helper. On the typed capacity signal it flushes the existing ordered batch, accumulates versions/conflicts, retries the same operation, and continues. A transport failure returns the ordinary pending state with the durable queued batch intact. A later retry reconstructs still-unqueued records from browser source state and resumes without loss.\n\n### Existing oversized files remain readable\n\nA legacy or externally produced outbox containing more than 1,000 valid operations is never sliced while reading. It can be drained in order. Capacity prevents adding another distinct operation until enough queued work has been sent.\n\n## Risks / Trade-offs\n\n- A snapshot larger than 1,000 operations produces multiple sequential flush batches. This is slower than bulk APIs but lossless and compatible with the current service contract.\n- Browser storage quota can still reject a write before the count limit; atomic `setItem` failure preserves the previous queue and surfaces the existing recovery path.\n- The source learning stores remain necessary for reconstructing records that could not yet enter a full outbox.\n\n
